# Changelog

## "Screen understanding" Phase 1: Gemini cloud vision provider, alongside the existing local Ollama one
- Owner's next step in the 2026-09-19 "full assistant" discussion (right after the PC-access boundary widening below): voice-driven screen understanding, so JARVIS can act on what's actually visible on the display. The heavy lifting for this already existed and was already thoroughly tested (RFC-007A/B/C -- desktop screenshot capture, a `VisionProvider` protocol, structured describe/OCR/find-element operations, agent-plan wiring via `desktop.capture_screen` + `vision.describe_desktop_capture` as MEDIUM-risk tool steps) -- but the only working provider was `OllamaVisionProvider`, a local vision model. Real-world testing earlier this session already showed local free models (`qwen2.5`, `llama3.2`) struggling with fiddly tasks; local *vision* models are weaker still at reading small on-screen text, and the owner asked directly whether a stronger option existed. Walked through the tradeoffs with her directly (OpenAI/Anthropic vision APIs have no free tier at all; Google Gemini does, at some real accuracy cost being a smaller/faster model line; a fully local vision model stays free and private but is weakest on small text) -- she chose Gemini's free tier.
- New `app/brain/vision/gemini_provider.py::GeminiVisionProvider`, implementing the exact same `VisionProvider` protocol as `OllamaVisionProvider` (`describe_image`, `extract_text`, `find_visual_element`, `verify_visual_crop`, `observe_full_frame`, `status`, `check_health`, `check_generation_ready`) by calling Google's `generateContent` REST API instead of a local Ollama server. Reuses the local provider's structured-output schemas and payload-parsing/evidence-building/sanitization helpers directly (imported, not duplicated) so both providers produce `VisionEvidence` in the exact same shape and are fully interchangeable from `VisionController`'s point of view -- every existing safety property of the vision pipeline (sanitized warnings/text, validated bounding boxes, grounding rules, evidence expiry) applies to Gemini output identically. Distinct Gemini-specific handling: HTTP 429 is reported as a clear free-tier-rate-limit message rather than a generic error; HTTP 401/403 as a clear "API key rejected" message; the configured model name is checked against a small allowlist of known image-capable Gemini model prefixes (`gemini-1.5`/`gemini-2.0`/`gemini-2.5`/`gemini-pro-vision`) so an unrecognized or future text-only model name fails with a clear message instead of a confusing error on first real use.
- New `VisionController.provider()` dispatch (`app/brain/vision/controller.py`): reads the already-existing (previously unused) `vision_provider` config value -- `"gemini"` constructs `GeminiVisionProvider`, anything else (including the unchanged default `"ollama"`) keeps the exact previous `OllamaVisionProvider` behavior. `vision_model` is reused as the model-name field for whichever provider is selected (same pattern already familiar from `ollama_model`/`intelligence_model`), so switching providers is `config set vision_provider gemini` + `config set vision_model gemini-2.0-flash` (or whichever current Gemini vision model she wants) -- no new model-name config key.
- New `vision_gemini_api_key` config key: a credential, not a tunable setting, exactly like the existing `location_shared_secret` (RFC-010) -- deliberately left out of `runtime_config.MUTABLE_KEYS`/`_ALLOWED_KEYS` so it can never be set via `config set` (which would otherwise put a real secret through voice transcription or shell history), and redacted (`<redacted>`) by `config show`/`config get`. Settable only by editing `config/config.json` directly, or -- the recommended option, so the key never sits in a config file at all -- left unset in favor of the standard `GEMINI_API_KEY` environment variable, which `GeminiVisionProvider` checks automatically whenever the config value is blank.
- Existing `desktop.capture_screen`/`desktop.capture_window` tool steps are unchanged and still MEDIUM risk, meaning JARVIS still asks for plan approval before capturing the screen at all (by default, unless `developer_mode` is on) -- this matters more now than before, since with Gemini selected, a captured screenshot's contents leave the machine for Google's API. Nothing about that approval gate was loosened here.
- New `tests/test_gemini_vision_provider.py` (18 tests): API-key resolution (config value vs. `GEMINI_API_KEY` env var, priority order), `status()` reporting not-configured without a key/model, known-vs-unknown vision model prefix recognition, HTTP 429/401/403/malformed-response handling, `describe_image()` happy path producing correctly-shaped `VisionEvidence`, `VisionController.provider()` dispatch (default stays Ollama; `vision_provider=gemini` selects the new provider with the configured model), and the credential-handling behavior of `vision_gemini_api_key` (rejected by `config set`, redacted by `config show`/`config get`). Full existing `tests/test_vision_runtime.py` suite (119 tests) re-run unchanged and still passes, confirming the local Ollama vision path is untouched.
- Not included here: the agent/router-level flow for saying "what's on my screen" out loud still goes through the existing intelligence/agent planner (unchanged) rather than a new deterministic command -- that part already worked before this patch and didn't need changing. Mouse/keyboard voice control and voice-driven program downloading/installing (the other two pieces from the same "full assistant" discussion) are separate, not-yet-started follow-ups, in that order per the owner's stated priority.

## PC-access boundary widening, Phase 1: `filesystem_allow_full_disk_access` + closing a relative-path loophole in the system-directory check
- Owner request (2026-09-19 discussion): JARVIS should be able to work with files anywhere on her system drive (Desktop, Documents, Downloads, ...), not just inside its own project folder, as the first step toward the larger "full assistant" wishlist (self-code-editing, Telegram messaging, browsing/automation, still explicitly deferred -- see the discussion in this session for the full boundary-setting conversation and the owner's explicit choices on each point). Before touching `get_trusted_roots()` at all, this session found a real security gap the widening would have exposed: `app/brain/filesystem/path_policy.py` and `app/brain/terminal/policy.py` each only ever checked a raw, literal path *argument string* for `Windows`/`System32`/`Program Files`/other-users'-`Users\<name>` segments (the terminal side checked only the final leaf component name, which is even weaker). That's harmless while the only trusted root is the project's own folder, but with the whole `C:\` drive trusted, a *relative* argument like `Windows/System32/evil.py` or `Users/someone_else/secrets.txt` never contains an absolute forbidden-looking string for either check to catch -- it only becomes a system path once resolved against the broad root, which neither check ever looked at.
- New `app/brain/filesystem/path_policy.py::is_forbidden_system_location(path)`: the single shared check now used by both subsystems, always evaluated against the fully resolved, canonicalized absolute path (never a raw argument) so a relative path can't slip past it however broad the trusted root is. Blocks any path containing a `windows`/`program files`/`program files (x86)`/`system32` segment anywhere, and any path under `Users\<name>` where `<name>` isn't the current OS user's own home directory (the owner's own home legitimately lives under `Users\<name>`, so that segment alone can't be an outright block). `app/brain/terminal/policy.py::_validate_local_path_argument` now calls this same function instead of its old leaf-name-only check, so the two subsystems can't drift apart on what "off limits" means.
- New `filesystem_allow_full_disk_access` config key (default `false`, in the runtime-mutable allowlist like other boolean settings): when `true`, `get_trusted_roots()` widens from just the project folder to the whole drive the project lives on -- `is_forbidden_system_location()` still applies on top regardless, so Windows/Program Files/System32 and other accounts' profiles stay off limits either way. An explicit `set_trusted_roots()` override (test-only today) still wins over this flag, same as before.
- New tests: `tests/test_path_policy.py` (new file -- `is_forbidden_system_location` against Windows/Program Files/another account's profile/the owner's own home/an ordinary path; `get_trusted_roots()` at the default, with the flag on, and with an explicit override; `resolve_path()` proving the relative-path loophole is actually closed with the flag on, and that ordinary relative paths still resolve normally). `tests/test_terminal_runtime.py` gains a regression test for the same relative-path loophole on the terminal side.
- This patch only adds the flag and the safety fix -- it does not turn full-disk access on by default (still `false`) and does not include the self-code-editing or Telegram work from the same discussion; those remain separate, not-yet-started follow-ups pending further input.

## Conversation prompt now tells the model to stay in the user's language
- Real-hardware report right after switching to a stronger local model (`qwen2.5:7b-instruct`, at the owner's request, to fix the AI/agent runtime's unreliable tool selection and reasoning -- see the entries below): a reply to Russian input came back with stray Chinese characters mixed into an otherwise-Russian sentence ("Как你能帮我？"). Root cause: `app/brain/runtime/conversation_runtime.py`'s `_SYSTEM_PROMPT` (sent ahead of the user's own message on every conversational turn) was entirely in English with no instruction about which language to reply in or to avoid mixing languages -- exactly the kind of prompt shape that invites code-switching on a multilingual model whose training leans heavily on English/Chinese data.
- `_SYSTEM_PROMPT` now explicitly instructs the model to always reply in the same natural language the user's message is written in, and to never mix languages or scripts within a single reply, even partially. This is a prompt-level mitigation, not a guarantee -- a local model can still misbehave -- but the instruction needs to actually be present, and previously it wasn't at all.
- New test in `tests/test_conversation_runtime_e2e.py` asserting the language instruction is actually present in the prompt handed to the provider.

## RFC-009: Russian "open ..." commands tolerate filler words and other verbs, Cyrillic site names
- Immediate real-hardware follow-up to the entry directly below: even after adding exact-phrase Russian aliases ("открой сайт <адрес>", "открой браузер", ...), the owner's actual spoken requests still missed them and fell through to the AI/agent runtime -- "открой сайт википедия" got "Command rejected by terminal policy" again, and "можешь открыть браузер"-style phrasing got an AI-hallucinated "I can't open the browser". Two real causes, both about natural speech not matching a fixed phrase: (1) a filler word ("пожалуйста") or a different verb ("зайди" -- go to, rather than "открой" -- open) breaks an exact-phrase/prefix match entirely; (2) the site was named in Cyrillic ("википедия"), which the previous `_KNOWN_SITE_ALIASES` map (Latin-alphabet keys only) didn't recognize, and it has no dot for the raw-domain fallback either, so it was rejected outright even once the command *did* route correctly.
- `app/brain/command_normalizer.py` gets a new keyword-based fallback (`_ru_open_intent_command`): if ANY recognized Russian "open"-type verb (открой/открыть/зайди/зайти/запусти/перейди/включи/...) appears anywhere in the phrase, it looks for a target keyword (браузер, блокнот, калькулятор, ютуб, гитхаб, гугл, or сайт + whatever follows it) anywhere after it -- order-and-filler-tolerant, instead of requiring the whole phrase to match exactly. This runs after the existing exact alias_map/prefix checks (which stay as the fast path for the common phrasing) and before the generic AI fallback.
- `app/brain/internet/web_actions.py`'s `_KNOWN_SITE_ALIASES` gains Cyrillic spellings of the same sites (гугл, гмайл/почта, ютуб, гитхаб, яндекс, вконтакте/вк, википедия) mapping to the same URLs as their Latin-alphabet equivalents, so naming a site in Russian works exactly like naming it in English.
- New tests in `tests/test_command_normalizer.py` and `tests/test_router.py` covering the exact filler-word/verb-variation/Cyrillic-name phrasing that failed on real hardware, end-to-end through `route_command`.
- Separately reported in the same session: the local `llama3.2` model (the `intelligence_model`/`ollama_model` config default) also botched a simple date-math question ("what year was I born, given my age and birthday") with garbled, incorrect reasoning, and refused an unrelated question citing "confidential information". Not fixed here -- both are underlying-model capability/behavior issues, not routing bugs, and the owner asked directly whether a stronger model is available; see the reply in this session for the options (larger local Ollama models vs. a cloud-hosted provider) and their tradeoffs. Worth a dedicated RFC/config change if the owner wants to pursue it, rather than a quiet default swap.

Both requests were transcribed correctly (confirmed from `logs/jarvis.log`: Russian detected with 0.99 confidence, capture/STT pipeline healthy) but then mishandled after that: neither phrase matches any deterministic router command (the router only recognizes English command text), so both fell through to the AI/agent runtime -- which, on the small local model this project uses (`llama3.2`), sometimes tried to reach the URL through the sandboxed terminal tool (rejected by terminal policy as "That path is not allowed", since a URL looks like a local file path to that validator) and sometimes just hallucinated a conversational "it's open now" reply without opening anything at all (confirmed directly by the owner asking again and getting contradictory answers).

This is deliberately a small, well-defined set mirroring the router's existing deterministic commands, not a general Russian translation layer -- open-ended requests still go through the AI/agent runtime exactly as before.
- New tests: `tests/test_command_normalizer.py` (Russian alias round-trips, `открой сайт` target extraction and case-folding), `tests/test_router.py` (`open google`, `open site` with a domain/known short name/no target/unrecognized bare word, and the exact real-world Russian phrasing that originally failed).

## RFC-009: hands-free at startup -- `voice listen`, and AI/voice on by default
- Owner's explicit follow-up request, now that `voice talk` reliably hears and responds quickly: stop having to type `voice talk` before every utterance, and stop having to type `ai on`/`voice on` at the start of every session -- JARVIS should be able to hear and act on commands as soon as it starts.
- `config/settings.py`: `ai_enabled` and `voice_enabled` now default to `true` (previously `false`). `ai on`/`ai off`/`voice on`/`voice off` still exist and still only apply for the current process (never persisted to `config/config.json`, unchanged from before) -- this only changes what a fresh, never-configured run starts with. This is a deliberate default-behavior change for a single-user local assistant, in the same vein as the speaker-verification opt-in change: no safety boundary is being removed, just the friction of re-enabling two features every single run.
- New `app.brain.router._voice_listen_loop()` (reachable via the new `voice listen` command): repeats the same push-to-talk turn `voice talk` already does -- capture with silence-triggered auto-stop, transcribe, route through the exact same `route_command` a typed message uses, speak the reply -- over and over, printing each reply as it happens, until a recognized stop phrase ("stop listening", "стоп", etc.) or Ctrl+C. Not wake-word detection (still explicitly deferred, see `docs/RFC-009_ON_DEMAND_VOICE_ASSISTANT.md`): it's push-to-talk automatically re-armed after each turn, not an always-on model reacting only to a trigger phrase. A stop phrase is intercepted in the loop's own `route_text` callback *before* it reaches the real router, so saying "stop listening" cleanly ends the loop instead of also being treated as an unrelated conversational turn and spoken back. `VoiceProviderError` ("No speech was recognized.") during a quiet gap between utterances is swallowed silently and the loop just re-captures -- expected here, not an error -- while `VoiceDisabledError`/`VoiceCaptureError` (voice turned off, mic broken) end the loop instead of retrying forever. A spoken "exit" still shuts JARVIS down cleanly (the loop propagates a "shutdown" reply the same way typing "exit" does).
- New `voice_listen_on_startup` config key (default `true`): `main.py` now calls this same loop automatically right after the startup banner, before the typed `You:` prompt ever appears, whenever it and `voice_enabled` both say to. Ending the startup listening session (stop phrase or Ctrl+C) falls back to the normal typed prompt rather than exiting JARVIS; only an actual "exit"/shutdown during that session ends the program. A broken mic or voice being off just falls back to typing silently, never spams retries.
- New tests: `tests/test_voice_listen_loop.py` (14 tests) covering the loop's stop-phrase interception, silent handling of empty-transcript gaps, structural-error termination, Ctrl+C, shutdown propagation, the `voice listen`/`voice stop listening` command dispatch, the new defaults, and `main._maybe_start_voice_listening_on_launch`'s three outcomes (skip, start-then-fall-back-to-typing, start-then-exit). Updated `tests/test_ai_router.py`, `tests/test_router.py`, `tests/test_conversation_runtime_e2e.py`, and `tests/test_agent_router.py` where they asserted the old disabled-by-default behavior/value directly rather than setting it up themselves.
- Docs: `docs/CONFIGURATION.md` gets `voice_listen_on_startup` and an "Enabled by default" note; `docs/RFC-009_ON_DEMAND_VOICE_ASSISTANT.md`'s supported/not-supported lists gain `voice listen` and a note distinguishing it from the still-deferred true wake-word engine.

## RFC-009: fix chunked capture regression -- one continuous stream, not one `sd.rec()` per chunk
- The chunked-capture latency fix below (previous entry) made things measurably *worse* on the owner's real Windows target machine, confirmed from real logs after a live test: capture that should have run 10.0s at most actually took `Voice turn timing: capture=22.06s` / `20.05s` / `20.68s` wall-clock -- and the audio actually captured during those 20+ second windows measured `rms=0.00004`-`0.0002` throughout (`Voice recording diagnostics (native_capture): ... very quiet recording`), a hundred-to-thousand-fold quieter than a genuine utterance captured minutes earlier in the same session (`rms=0.03`-`0.07`). The owner's actual speech was barely reaching the recording buffer at all, and every one of those attempts logged `Voice capture ran to the full 10.0s window (no speech detected, ...)` -- auto-stop never even got the chance to help, because the recorded signal never looked like speech in the first place.
- Root cause: `_capture_native_audio()` issued one `sd.rec()`/`sd.wait()` call *per 0.2s chunk* -- each of which opens and closes the audio device stream from scratch. On this real hardware that cost roughly 200ms of open/close overhead per chunk (measured directly from the timing logs: ~50 chunks x ~200-240ms extra = the observed 10-12s of excess wall-clock time), and appears to have also kept the "Microphone Array" driver's own signal processing (the same array-mic quirk `DEFAULT_INPUT_DEVICE`'s hardware note already documents) from ever settling into capturing real signal, since it was being torn down and restarted every 200ms.
- Fix: `_capture_native_audio()` now opens a single `sd.InputStream(...)` once for the whole recording and reads each `_CAPTURE_CHUNK_SECONDS` chunk from it via `stream.read(frames)`, never closing/reopening between chunks -- the same chunked analysis loop (noise-floor calibration, active-threshold detection, trailing-silence timeout) as before, just fed by one continuous stream instead of many short-lived ones. This is the standard `sounddevice` pattern for incremental/VAD-style capture; `sd.rec()` was only ever meant as a single-shot convenience wrapper, not something to call in a tight loop.
- Rewrote every test in `tests/test_voice_runtime.py` that mocked `sd.rec()`/`sd.wait()` (mic-active flag, native device settings, downmix/resample, both `_capture_native_audio()` early-stop tests, all four `VoiceRecordingDiagnosticsTests`, the silence-trim regression test, and the device-failure test) to instead mock `sd.InputStream(...)` via a new shared `_FakeInputStream`/`_patch_input_stream` test double modeling the real one-stream-per-recording usage -- so the test suite itself now exercises (and would have caught) the per-chunk-stream-reopen shape of the original bug, not just the analysis logic layered on top of it.
- Also fixed a real, unrelated bug this same real-hardware test run surfaced independently: `tests/test_voice_runtime.py::SpeechBrainModelLoadingTests::test_clear_broken_symlinks_removes_only_dangling_entries` creates a real symlink to exercise `_clear_broken_symlinks`, but on a plain Windows account without Developer Mode/admin, symlink creation itself raises `OSError: [WinError 1314] A required privilege is not held by the client` -- the exact condition that test class exists to work around, meaning the regression test for the Windows symlink-privilege bug could never get past its own setup on the very machine it's meant to protect. Now skips with a clear reason instead of failing when symlink creation isn't possible in the current environment.

## RFC-009: `voice talk` latency fix (chunked capture, stop as soon as you stop talking)
- Owner-reported: after switching to plain voice control (no speaker verification), a real end-to-end `voice talk` run worked -- transcribed real speech and executed real actions (opening Notepad, opening the browser) -- but took roughly 7 seconds *after* the owner finished speaking before the action ran. Root cause: `record_from_microphone()` always recorded for the full fixed duration (`DEFAULT_PUSH_TO_TALK_SECONDS`, previously 6s) via one blocking `sounddevice.rec()` call, with no way to know speech had already ended partway through that window -- so most of the reported wait was simply the mic continuing to record silence after the owner had stopped talking, not STT/routing/TTS being slow.
- `app/brain/voice/audio_io.py` replaces that single blocking call with a new `_capture_native_audio()`: it records in small `_CAPTURE_CHUNK_SECONDS` (0.2s) chunks via repeated `sd.rec()` calls, calibrates each recording's own noise floor from its first chunk, and stops as soon as `voice_talk_silence_timeout_seconds` of trailing silence follows detected speech -- once at least `voice_talk_min_duration_seconds` has elapsed, so a very short opening word can't trigger an instant cutoff. `DEFAULT_PUSH_TO_TALK_SECONDS` was raised from 6s to 10s accordingly: it's now just a safety ceiling (for background noise/heavy breathing that never reads as real silence), not the typical recording length. New config keys, all in the runtime allowlist and CLI-configurable: `voice_talk_auto_stop_on_silence` (default `true` -- set `false` to always record the full window, restoring the old fixed-duration behavior), `voice_talk_silence_timeout_seconds` (default `1.0`, range 0.2-10.0), `voice_talk_min_duration_seconds` (default `1.0`, range 0.2-10.0).
- Frame counts inside `_capture_native_audio()` are tracked as integers (total frames = `round(max_duration_seconds * native_sample_rate)`), not accumulated as floating-point seconds compared each iteration -- an early version of this fix compared accumulated float seconds against the duration directly, which floating-point drift could leave one frame short of a full chunk, triggering a spurious near-empty extra `sd.rec()` call at the very end.
- Every capture now logs its outcome unconditionally, not just on early stop: either "auto-stopped after Xs" (with how much trailing silence triggered it and the calibrated noise floor) or "ran to the full Xs window" (naming why: auto-stop disabled, no speech ever detected, or trailing silence never reached the configured timeout) -- so a future latency investigation never has to guess which path a given recording took.
- Also added per-stage timing diagnostics to `app/brain/voice/controller.py`: `handle_voice_turn()` now logs `verify`/`transcribe`/`route`/`tts` durations and `push_to_talk_local()` logs the capture duration separately, all as one `Voice turn timing: ...` line -- so if latency remains after this fix, the logs will show exactly which stage is the bottleneck (e.g. a large STT model, slow AI/LLM planning, or TTS synthesis) instead of guessing again.
- Added `tests/test_voice_runtime.py::test_capture_native_audio_stops_early_after_trailing_silence` and `test_capture_native_audio_runs_full_duration_when_auto_stop_disabled` exercising `_capture_native_audio()` directly; updated `test_record_from_microphone_uses_configured_native_device_settings` (now expects 5 chunked `sd.rec()` calls instead of 1) and `test_record_from_microphone_trims_silence_surrounding_speech` (its fake capture now simulates the intended silence/speech/silence envelope across however many chunked calls it takes, instead of assuming one call spanning the whole recording). Added `tests/test_runtime_config.py::test_voice_talk_auto_stop_settings_default_and_are_configurable` for the three new config keys' defaults, round-trip, and validation.
- Not yet addressed: the owner's second request in the same report -- not having to type `voice talk` before every utterance for more continuous/hands-free voice control. That's a separate, larger design question (a continuous-listening loop vs. true wake-word detection, the latter explicitly out-of-scope in the original RFC-009) and is being proposed separately rather than implemented unilaterally.

## RFC-009: speaker verification made opt-in (owner's explicit request)
- After the exhaustive real-hardware investigation above (mic pipeline, SpeechBrain loading, silence trimming, and two rounds of threshold recalibration), the owner decided the remaining friction wasn't worth it: they want plain voice control -- JARVIS hears and acts on any voice -- without speaker recognition gating every utterance. This is a deliberate product decision, not a bug being patched over: even with every mechanical cause fixed, the enrolled owner's own genuine similarity score continued to vary widely (0.23-0.68), so the verification step was rejecting the owner's own genuine speech close to as often as it accepted it.
- Added `voice_require_speaker_verification` (default `false`) to the runtime configuration allowlist. `VoiceController.handle_voice_turn()` now only calls `_verify_owner()` when this is enabled; with it at the new default, `voice talk`/`/voice/turn` transcribe and route any voice exactly like typed input, and no enrollment is required at all. The enrollment/verification subsystem itself (SpeechBrain ECAPA-TDNN, `voice enroll`/`voice forget me`, the similarity-threshold machinery) is not removed -- `config set voice_require_speaker_verification true` restores RFC-009's original always-on hard-boundary behavior in full.
- **This changes what the project's own hard-boundary promise means by default.** RFC-009's "only the enrolled owner's voice is ever processed" was motivated by two things (see `docs/RFC-009_ON_DEMAND_VOICE_ASSISTANT.md`'s "Hard boundary" section, updated accordingly): consent around processing a second identifiable person's speech, and consistency with `docs/VISION_ROADMAP.md`'s "unverified speakers cannot issue owner commands" permanent decision. With verification off, *any* voice reaching the microphone is transcribed and treated as a command, not just the owner's -- an intentional, explicit trade-off for a single-user local device, not a case of quietly disabling a security feature to make a bug go away. Anyone who wants the original behavior back (e.g. if other people's voices might reach the mic) sets the config value back to `true`.
- `voice status` now reports a `Speaker verification required:` line alongside the existing enabled/mic-active/enrolled lines.
- Updated `tests/test_voice_runtime.py`: existing verification-gate tests (rejecting a non-owner voice, requiring enrollment first, dimension-mismatch/threshold logging, the field-observed-similarity regression test) now explicitly set `voice_require_speaker_verification=True`, since that behavior is no longer the default; added new tests for the opt-in default itself (a stranger's voice is now accepted, no enrollment is required, `voice status` reports the requirement state). Added `tests/test_runtime_config.py::test_voice_require_speaker_verification_defaults_off_and_is_configurable` for the new config key's default, round-trip, and type validation.

## RFC-009 verification threshold, second recalibration (0.6 -> 0.4, again data-driven)

## RFC-009 verification instability: root cause found and fixed (silence trimming)
- Root cause confirmed from real-hardware logs produced by the diagnostics added just before this: every live `voice talk` recording had `active_speech_ratio` between `0.115` and `0.200` -- i.e. 80-88% of the fixed 6-second capture window was silence/room noise, not speech -- with leading silence `0.87-1.2s` and trailing silence `2.79-3.84s` that differed between attempts. `clipping_ratio` was `0.0000` on every attempt and per-channel peaks were even (e.g. `[0.2815, 0.2815, 0.2815, 0.2815]`), so this was not a mic-level, clipping, or channel-imbalance problem: it was the *content* of the recording. `voice talk` starts recording for a fixed duration immediately, with no "get ready" cue, so how much silence surrounds the actual utterance -- and therefore what fraction of the waveform SpeechBrain's ECAPA-TDNN encoder actually has to work with -- depends purely on when the user happens to start/stop talking relative to that fixed window. Feeding the encoder a waveform that is mostly silence, in a different ratio and position every attempt, produces a correspondingly unstable embedding for the same genuine speaker.
- `app/brain/voice/audio_io.py` adds `_trim_silence()`, which crops a recording down to its speech-bearing region (using the same sliding-window energy activity detector the diagnostics already used, factored out into `_compute_window_activity()` so the trim boundaries always match what's logged) plus 0.2s of padding on each side. `record_from_microphone()` now applies it as the final step, after downmix and resample, before returning -- so both `voice enroll` and `voice talk` (which share this one function) get a consistently speech-dense clip instead of a fixed-duration window padded with an unpredictable amount of silence. Falls back to returning the untouched recording if no activity is detected at all, or if trimming would leave under `MIN_TRIMMED_SECONDS` (0.5s) of audio, so a genuinely silent or very brief recording is never turned into an almost-empty clip.
- A synthetic reconstruction of the reported field shape (6s total, ~1.2s leading silence, ~2.79s trailing silence, speech only in between) verifies the fix: `active_speech_ratio` rises from `0.335` to `0.840` and the clip shrinks from `6.000s` to `2.410s` after trimming.
- `voice_verification_threshold` was **not** changed (still `0.6`) and speaker verification was **not** disabled or bypassed at any point in this investigation or fix, per explicit instruction.
- New diagnostics stage: `Voice recording diagnostics (trimmed):` logs the same fields as `native_capture`/`preprocessed` for the final, trimmed audio actually handed to STT/verification, plus an info line naming how much silence was cut (e.g. `Trimmed 3.590s of leading/trailing silence from recording (6.000s -> 2.410s) ...`) whenever trimming actually changes the length.
- Added regression tests (`tests/test_voice_runtime.py::VoiceSilenceTrimFixTests`): `_trim_silence()` crops leading+trailing silence while preserving the speech interior, leaves a fully-active signal untouched, falls back to untouched audio on a fully-silent recording and on a too-short trim result, and `record_from_microphone()` itself shrinks a synthetic silence-speech-silence native capture from 6s down to well under half that while logging the new `trimmed` diagnostics stage.

## RFC-009 verification threshold recalibration (data-driven, not blind)
- Root cause of `voice talk` rejecting the enrolled owner, found from the diagnostics added previously: a real `voice enroll` + `voice talk` run on real hardware logged `Voice enrollment finalized: 3 samples, ... pairwise_similarity=['0.6131', '0.5049', '0.6662'], sample_to_average_similarity=['0.8282', '0.8985', '0.8353']` followed by `Voice verification: ... similarity=0.7311 threshold=0.7500 result=reject`. Both embeddings were length 192 (no dimension mismatch), the audio was a well-formed non-silent signal, and the genuine owner's own live verification attempt scored 0.7311 -- just 0.019 below the old default threshold of 0.75. This was a miscalibrated threshold, not a broken pipeline: `speechbrain`'s own `SpeakerRecognition.verify_batch()` reference implementation for this exact `spkrec-ecapa-voxceleb` checkpoint defaults to `threshold=0.25`, far below `0.75`.
- `voice_verification_threshold`'s default changed from `0.75` to `0.6` (`config/settings.py`, `app/brain/configuration/runtime_config.py`, and the inline fallback in `app/brain/voice/controller.py._verify_owner()`): below every genuine-match score observed on real hardware so far (margin >=0.13 to the live 0.7311 result), while staying well above `speechbrain`'s own `0.25` reference boundary for this model. Still fully configurable via `config set voice_verification_threshold <value>` -- documented as a data-driven starting point, not a universal constant, since a different microphone/room/owner may need retuning using the similarity scores now logged to `logs/jarvis.log`.
- Found and fixed a second, previously-unnoticed bug while making that retuning actually possible: `config set` never parsed a float value at all -- only `"true"`/`"false"` and a plain-digit integer -- so `config set voice_verification_threshold 0.65` silently returned "Configuration change rejected." with nothing indicating a parsing gap (rather than an invalid value) was the real cause. `app/brain/router.py`'s `config set` handling now also tries `float()` as a last resort before giving up and leaving the value as a string, so existing string-valued settings (model names, paths) are unaffected.
- `VoiceController.verification_provider()` (found while tracing this same bug) previously constructed a brand-new `SpeechBrainVerificationProvider` -- reloading the whole ECAPA model from disk -- on every single `enroll_sample()`/`handle_voice_turn()` call; now cached on the controller instance and built once.
- Added regression tests: the new `0.6` default, that it is retunable via `config set` (including the float-parsing fix, and that string-valued keys are unaffected), and a test that replays the exact field-observed 0.7311 similarity score and asserts it is now accepted rather than rejected.

## RFC-009 SpeechBrain model-loading fix (Windows symlink privilege)
- Root cause of `voice enroll`'s "Speaker embedding failed." found via the diagnostic logging added previously: SpeechBrain's `fetch()` defaults to `LocalStrategy.SYMLINK`, which symlinks each downloaded model file from Hugging Face's cache into `savedir`. On a plain Windows account (no Developer Mode, not running as administrator), `pathlib.Path.symlink_to()` raises `OSError: [WinError 1314] A required privilege is not held by the client`. The logged pre-flight audio diagnostics confirmed this was never an audio problem: `shape=(1, 64000) dtype=torch.float32 sample_rate=16000 n_samples=64000 has_nan=False has_inf=False` -- a well-formed mono 16 kHz signal reached `encode_batch` correctly; the crash was purely in model loading, inside `speechbrain.utils.fetching.link_with_strategy()`.
- `SpeechBrainVerificationProvider._classifier_instance()` now passes `local_strategy=LocalStrategy.COPY_SKIP_CACHE` to `EncoderClassifier.from_hparams(...)`. This tells SpeechBrain to download the model straight into `savedir` via `huggingface_hub`'s own `local_dir=` download path, which writes a normal file and never calls `symlink_to` -- confirmed by re-running the (now-fixed) code path against the real `speechbrain`/`huggingface_hub` packages: the only remaining failure in this environment is the network layer itself (this sandbox's outbound proxy blocking huggingface.co), with no `symlink_to` anywhere in the resulting traceback. No Developer Mode, administrator rights, or other Windows security setting change is required.
- Added `_clear_broken_symlinks()`, run before every model-load attempt: it removes any dangling symlink left behind in `download_dir` by an earlier attempt that used the old default `SYMLINK` strategy and failed partway through, so a stale broken entry from before this fix cannot interfere with a fresh `COPY_SKIP_CACHE` download. A real file, a working symlink, or a directory that does not exist yet are all left untouched. This means `data/models/spkrec-ecapa-voxceleb` never needs to be deleted by hand after upgrading -- the next `voice enroll` self-heals it.
- Added regression tests: `SpeechBrainVerificationProvider._classifier_instance()` is asserted to request `LocalStrategy.COPY_SKIP_CACHE` (never `SYMLINK`) via `speechbrain`/`torch` stubbed through `sys.modules`, so the test does not require the real (heavy) packages to be installed; `_clear_broken_symlinks()` is tested to remove only a dangling symlink while leaving a real file, a working symlink, or a missing directory untouched.

## RFC-009 mic pipeline fix
